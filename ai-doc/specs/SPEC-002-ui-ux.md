# SPEC-002｜內部計算工作台 UI／UX 契約

文件狀態：`RD Implementation Ready`  
版本：`1.6`
日期：`2026-07-17`
權威範圍：資訊架構、畫面、狀態文案、CTA、RWD、accessibility 與 UI QC

## 1. UX Intent

- 使用者：取得試用網址的鉦富同事；第一版不要求帳號或角色，同一位使用者可完成一人作業與核發。
- 使用情境：收到客戶資料後，可能只知道人數、面積、設備能力或舊版公升容量，需要快速得到可追溯結果。
- 使用者心智模型：選擇「我知道什麼、要算什麼」，再依提示補資料；不應先理解公式代碼。
- 主要任務：建立案件、完成至少一個有效計算軌、預覽並核發報告。
- 成功狀態：5 秒內知道案件狀態、哪一軌完成、下一步按什麼、有哪些限制。
- 自然下一步：資料不足就補任一可用軌；計算有效就由目前使用者直接預覽並核發，不需切換帳號。
- 最高風險誤解：把提醒當阻擋、把舊版公升數當現行能力、把設計需求計算誤認為產品或證書符合性判定。
- 高風險操作：啟用規則版本、核准 override、核發正式報告。
- 使用思考習慣：`#目的`、`#使用者視角`、`#可驗證性`、`#系統描繪`。

## 2. UX 原則

1. 主畫面先回答「我在哪裡、現在狀態、下一步、風險」。
2. 客戶任務名稱優先於公式與方法代碼。
3. 每一畫面只保留一個 primary CTA。
4. 非阻擋提醒不能使用禁止語意或讓 primary CTA disabled。
5. 技術細節、完整公式、來源 hash 與 raw trace 降層到 drawer／details／audit。
6. 現行與舊版視覺對稱，但單位、標籤、來源時效與限制必須明顯不同。
7. 正式核發前提供範圍摘要與報告預覽。

## 3. Information Architecture

| Route                | 畫面           | 主要使用者     | Primary CTA                                           |
| -------------------- | -------------- | -------------- | ----------------------------------------------------- |
| `/cases`             | 案件清單       | 內部計算使用者 | `建立案件`                                            |
| `/cases/new`         | 任務與模式精靈 | 工程           | `下一步：填寫資料`                                    |
| `/cases/{id}`        | 案件工作台     | 內部計算使用者 | 依狀態顯示 `開始計算`／`預覽並核發報告`               |
| `/cases/{id}/report` | 報告預覽與版本 | 內部計算使用者 | `核發此版本` 或 `下載已核發報告`                      |

首屏不常駐公式教學；每頁提供可鍵盤操作的 `查看計算依據` 或 `使用說明` drawer。

## 4. 案件清單

採表格／清單為第一視覺，不使用大型 KPI 卡。

欄位：案件編號、客戶、地點、任務、模式、計算狀態、生命週期、完成軌、最後更新、負責人、下一步、操作。

Toolbar：搜尋、狀態、模式、任務、負責人、日期篩選；篩選結果與 URL query 同步。

點列開啟右側 drawer，顯示摘要、完成軌、提醒、最新報告與 audit；drawer 不推擠主清單。桌面 drawer 自行捲動，mobile 使用全寬 drawer。

Empty state：

> 目前還沒有案件。建立第一筆案件後，即可依人數、面積或設備能力開始計算。

Primary CTA：`建立案件`；每筆案件提供 `刪除案件` 操作，確認後刪除該案件的全部修訂與關聯資料。

## 5. 建立案件精靈

### Step 1：你要解決什麼問題？

以五個任務卡呈現，不先顯示 T code：

- 我知道每日用餐人數，要換算流量。
- 我知道每日用餐人數，要規劃設計需求。
- 我知道廚房與用餐區面積，要換算流量。
- 我知道廚房與用餐區面積，要規劃設計需求。
- 我知道設備能力／有效容積，要反推等效人數及面積。

每卡只有一個 `選擇此任務` 動作。

### Step 2：選擇計算模式

- `內政部給排水規範（附錄 5）`：預設選中，短說明「依水量與油脂量計算設計需求」。
- `臺北市工務局衛工處設計說明`：短說明「依設計處理水量與有效容積計算設計需求」。
- `不同計算依據對照`：短說明「兩份資料來源分開計算；任一份有效即可預覽並核發」。

完整法規說明放 drawer，不在卡片放長文。

### Step 3：案件基本資料

客戶、地點、案件名稱、用途、資料提供者與證據皆為選填，label 必須明示「選填」；空白資料不得阻擋建立案件。餐飲類型不在此步驟重複詢問，移至案件工作台的內政部給排水規範（附錄 5）計算資料。

未填案件名稱時，後續清單與工作台以系統案件編號作顯示識別；未填客戶或地點時顯示「未填客戶」或「未填地點」，不得產生空白標題或無法辨識的列。

## 6. 案件工作台

### 6.1 頁面層級

1. 頁名與案件識別。
2. 狀態摘要：生命週期、計算狀態、目前完成軌。
3. Primary CTA。
4. 短風險／提醒。
5. 輸入與結果工作區。
6. 完整來源、公式與 audit drawer。

### 6.2 多軌 layout

桌面／laptop：兩份計算依據使用兩欄或分段並列；欄位標頭固定顯示來源名稱、單位系統、來源地位、完整性 badge。

Mobile：垂直堆疊，不做左右比較表；完成軌置前，不足軌置後並保留 `補齊此軌`。

不得用顏色作唯一識別；軌名與文字 badge 必須存在。

### 6.3 動態輸入

只顯示所選任務與模式需要的欄位：

- 內政部給排水規範（附錄 5）人數／面積／能力反推：每日用餐人數、面積、餐飲類型、油脂／殘渣清除週期、Q／G 設計能力與證據。
- 臺北市工務局衛工處設計說明人數／面積／能力反推：餐期、人數、面積、密度、翻桌率、q、t、exact k、有效容積與理由。

每個數值欄位需與單位同列呈現，且不得只依賴 placeholder 表示單位；跨單位轉換需顯示轉換摘要。
餐飲類型不得在新案件頁預先代選；內政部給排水規範（附錄 5）計算開始前，使用者必須在工作台明確選擇。

工作台需顯示低干擾的輸入完整性 badge，至少涵蓋：標準條件完成、使用特殊條件完成／使用特殊條件、僅完成一份依據、使用設備資料、工程選值已記錄與缺少選值理由。

計算資料主表需採固定矩陣呈現：屬性、條件、輸入值、說明。屬性以短 chip 固定於第一欄，條件名稱與輸入值分欄對齊，說明只保留固定 icon 欄；一般輸入欄位需壓縮為單列呈現，不得在窄版拆成屬性／條件／輸入值三段堆疊。不得用色條或每列長文字說明造成欄位噪音。輸入框本身採一致的藍色系樣式，來源類型完整說明集中於可收合圖例，並在報告輸入條件表中完整呈現。來源類型至少包含「案件資料」「工程選值」「設備資料」「實測資料」「覆寫值」。

內政部 `actualUseMinutes` 屬於特殊條件；UI 必須放在「特殊條件／有資料再填」或同等降層區塊，不得放入主要必填流程。填寫後，客戶報告需標示為覆寫值並保留來源／理由。

臺北市 q、t、exact k、有效容積等非單純案件事實的工程參數，需結構化保存選值來源類型、選值原因與證據備註；可向下組合成既有 `selectionReason`，但 UI 不得只依賴單一長文字欄位。q 欄位需提供臺北市設計說明用水量表摘要，讓使用者可看見餐廳類別、q 範圍、翻桌率與密度參考。

## 7. 計算結果

案件工作台與客戶報告共用同一份「本次設計結果」顯示模型，以輸出項目為列、計算依據為欄，不得在案件頁另做各軌結果卡片或自行定義單位。

結果表顯示：

- 結論數值與正確單位。
- 同一輸出項目在各計算依據下的結果，未產出的項目顯示「此依據無法計算」，缺少有效結果則顯示「未完成」。
- 兩份計算過程統一使用「設計處理水量」「清除週期油脂量」「有效容積」；來源為 `L/h` 的設計處理水量須保留原始結果，並另列除以 60 後的 `L/min` 統一比對值。
- 清除週期油脂量 `G` 的單位固定為 `kg`，不得寫成每日油脂量或 `kg/day`。
  raw、規則版本與來源資料不直接顯示在案件頁結果主區；主畫面只顯示與報告一致的 adopted value、統一單位與必要限制。

案件工作台採用輸入導向的計算提交：送出計算的按鈕固定置於「計算資料」結尾。尚未有計算狀態、評估或結果時顯示 `開始計算`；已有任一計算狀態、評估或結果後顯示 `重新計算`。`開始計算` 與 `重新計算` 使用與 `預覽並核發報告` 一致的主要按鈕呈現。結果區只保留「本次設計結果」與後續流程 CTA，例如 `預覽並核發報告`，不得再重複放置重新計算按鈕。

結果頁不顯示產品型號、證書或匹配狀態。限制摘要固定提供「本系統未執行特定產品或證書符合性判定」，完整說明降層至報告限制與方法 drawer。

## 9. 報告預覽與核發

核發前顯示 preview summary：案件、revision、模式、完成軌、未完成軌、提醒、編製 actor、報告頁數／產生狀態與快照 hash 短碼。此頁不提供送審、覆核 checklist 或退回功能。

Primary CTA：`核發此版本`。核發屬正式紀錄，需確認 modal：

> 核發後此版本與快照不可修改。若內容變更，需建立新修訂版。

確認按鈕：`確認核發`；取消：`返回預覽`。不要求輸入長字串確認。

### 9.1 客戶報告資訊架構

- 客戶報告不使用獨立空白封面；第一個資訊區塊直接呈現案件資料與「本次輸入條件 → 計算依據 → 本次設計結果」。
- 輸入條件依實際完成的計算依據分組，欄位固定包含條件名稱、輸入值、類型與來源／理由；未使用欄位不顯示，缺值不得顯示為 0。
- 輸入條件的類型用於溝通來源，至少包含「案件資料」「工程選值」「設備資料」「實測資料」「覆寫值」。公式代入表仍可使用「本案條件」「計算依據參數」「計算中間值」表示數值在算式中的角色。
- 結果使用對照表；設計處理水量在對照表一律使用 `L/min`，不得在同一列混用 `L/min` 與 `L/h`。來源原始單位只保留於完整計算過程，並緊接列出 `L/min` 統一比對值。清除週期油脂量 `kg` 與有效容積 `L` 不進行數值比較。
- 「未完成」代表該計算依據缺少有效結果；「此依據無法計算」代表該來源本來就不產出此項目，兩種狀態須以文字區分。
- 完整計算過程中，每個方法先列「本方法使用的條件」，每個步驟依序列公式、具名代入內容、數值算式、計算結果與必要的統一比對值。
- 具名代入內容固定包含符號、代表內容、數值、單位、資料角色；資料角色只使用「本案條件」「計算依據參數」「計算中間值」。
- 客戶報告不顯示內部檢查資料、audit、checksum、內部狀態、工程責任、產品型號或證書匹配內容。

## 10. 規則管理

### 規則版本

清單顯示 code、version、來源、狀態、有效期、checksum、回歸結果。ACTIVE 版本不提供編輯，只有 `建立新版本`。

啟用前顯示參數差異、受影響方法與回歸結果；未通過時 `啟用版本` disabled 並顯示原因。

## 11. Responsive 與 scroll owner

必測 viewport：`1440×900`、`1024×768`、`390×844`。

- 1440：完整清單、雙欄結果、右側 drawer。
- 1024：維持可比較欄位；必要時結果改為上下區塊，不得水平裁切主要 CTA。
- 390：表格改 stacked list，drawer 全寬；所有主要流程可完成，不要求水平捲動。
- 同畫面最多一個主要垂直 scroll owner；drawer 開啟時 drawer body 自行捲動並阻止 scroll chaining。
- 固定底部 CTA 不得遮住欄位、錯誤或鍵盤輸入。

## 12. Accessibility

- 所有 input 有可見 label、程式化關聯與就近 error。
- 完整鍵盤操作；focus order 與畫面順序一致。
- focus ring 可見；drawer／modal 開啟時 focus trap，關閉後回原觸發點。
- `Escape` 關閉暫時 drawer／popover／modal；正式輸入不因 Escape 丟失。
- 狀態不只靠色彩；文字與 icon 共同表達。
- 一般文字與控制項符合 WCAG AA 對比。
- 計算完成與錯誤使用適當 live region，但不重複朗讀整頁。

## 13. Visible Error Gate

任何 critical route 若可見以下內容，UI QC 失敗：

- `.inline-error`／`[role=alert]` 中未處理 runtime 錯誤。
- `HTTP 4xx/5xx`、`Not Found`、`Internal Server Error`。
- 可見 `/api/...` route 或 stack trace。
- 載入失敗但沒有重試／安全返回。

Build、lint、unit test 不能取代真實瀏覽器驗證。
